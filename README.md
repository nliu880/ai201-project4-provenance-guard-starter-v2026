## What This Does

This project takes a text submission through an API request in JSON format and judges to see if it was generated using AI or written by a person. The decision is made through a combination of LLM usage and style features, such as sentence length and vocabulary breadth. The decision is returned in JSON format with additional information, such as a `content_id`, and is also saved to an audit log. Users may choose to appeal the decision through another request using the previously generated `content_id`, where it be noted in the audit log.

<!-- The path a submission takes, from arriving to the label a reader sees.
     Six or seven steps — this is the trace you wrote in Milestone 1. -->

     1. Text goes through the POST request in JSON format, along with the `creator_id`. 
          a. Example: {"text": "Sample text.","creator_id": "sample_id"}.
     2. On the back end, the text is retrieved from the JSON formatting. Nothing is created or removed at this point.
     3. The text is passed to the detector (`detector.py`) and returns a score regarding how likely it is that this text was generated by an AI.
     4. A `content_id` is generated for this text.
     5. The text is passed to `stylometry.py`, a function to measure the style of some writing, and returns a score regarding that.
          a. This information, along with the detector model score in Step 3 and the `content_id`, are added to the audit log.
     6. A guess (human/AI/unsure), confidence score for that guess, and label are created based on the detector model score and style score for the text. # look here something about guess vs label
     7. Return the `creator_id`, `content_id`, guess, confidence, label, and two scores in JSON format for the user to see.
          a. {"confidence": "0.5", "content_id": "sample_content_id", "creator_id": "sample_id", "guess": "unsure", "label": "not built yet", "model_score": null, "style_score": null}

## Signals and Scoring

<!-- For each signal: what property it measures, why that might differ between
     human and AI writing, and WHAT IT CAN'T SEE.

     The blind spot is not optional. If you can't name it you don't understand
     the signal yet — and unit 8's attack set is built out of blind spots. -->

### Signal one — the model signal

**What it measures:** This measures how predictable some text is, a measure known as perplexity.

**Why that might differ between human and AI writing:** As AI generated text is based on the next most probable word, text produced by a model is text that is easy to predict. 

**What it can't see:** Sometimes the most common or predictable sequence of words is just that (ex: "I like cats more than dogs."). It can still be written by humans. The detector model score just looks for how predictable the text can be, which doesn't always mean anything by itself. 

### Signal two — the style signal

**What it measures:** This measures the shape and style of the text: sentence length, word variation, punctuation usage, etc.

**Why that might differ between human and AI writing:** AI commonly generates sentences of middling length and with even vocabulary. Human writing typically varies more, using larger vocabulary in metaphors and using differing sentence lengths for different impact. 

**What it can't see:** This score is composed of numerical components: how long a sentence is, how many different words, etc. It does not actually consider how the words are put together or what the context might be, so adding Oxford commas would raise this score without changing the core meaning.

### The combining rule

<!-- Write the rule in words, then give the numbers. What happens when the two
     signals disagree? -->

**The rule:** If the style scores differ by more than 0.15, then a weighted average will be used, with more weight given to the detector score. Otherwise, use the mean.

**The numbers:** 

- If |`detector_score` - `style_score`| ≥ 0.15: `detector_score` * 0.65 + `style_score` * 0.35
- Otherwise: `detector_score` * 0.5 + `style_score` * 0.5

**Where it lives:** `scoring.py::combine_signals`

## Label Variants

<!-- The exact text of all three labels, as a reader would see them, and the
     score range each covers.

     Write them for someone who has never heard the word "threshold". -->

| Label | Score range | The exact text a reader sees |
|---|---|---|
| high-confidence human | `score` ≤ 0.375 | `"We believe this text was generated by a person."` |
| unsure | 0.375 < `score` < 0.625 | `"We aren't sure whether this text was written by a person or generated by an AI model."` |
| high-confidence AI | `score` ≥ 0.625 | `"We believe this text was generated by an AI model."` |

**Why I worded the "unsure" one this way:**
<!-- It's the hardest of the three. It has to admit uncertainty without
     sounding like an accusation, because the person reading it may well have
     written every word themselves. -->

The way the sentence is phrased just states the uncertainty and does not delve further into any reasons. All it says is that the model cannot tell and therefore doesn't know.

## Rate Limiting

**My limits:** 5 per minute, 50 per day

**Why those numbers and not others:**
<!-- Think about two people: a real writer submitting their own work a few
     times an hour, and a script sending a thousand variations to map your
     thresholds. Your numbers have to be liveable for the first and hostile to
     the second. -->

     A real writer should submit their work once, and then depending on the result, edit it before making another submission. Even if the writer is just spam submitting to see if the system is functioning or if its lagging, they still would not be submitting too many times a minute, hence the limit of 5.

     Similarly, a writer can only spend so many hours a day editing their work between attempts or submitting different pieces. In the first situation, true editing/rewriting and then resubmitting should take up far fewer than 50 attempts. In the second scenario, a writer wouldn't be able to produce 50 pieces of writing a day, unless they are using AI, in which case the model classifier is a moot point.

**What a caller counts as:** <!-- per address, or per creator_id? They fail
differently — one script can look like a thousand callers, and one household
can look like one. --> Callers are counted by `creator_id`.
